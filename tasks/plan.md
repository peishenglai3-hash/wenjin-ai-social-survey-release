## 1. 目标和硬约束

本计划把已批准的规格拆成可回滚的垂直切片。每个切片都必须在本地验证、审查并形成原子提交后才能进入下一切片；不把“最后一次性重构”作为交付策略。

硬约束：

1. 保留现有稳定核心代码、页面和测试基线；不得为了新架构删除未证明冗余的核心路径。
2. 新功能默认关闭或只对显式配置/授权可见；未完成能力不能通过默认启动路径改变旧行为。
3. 真实 provider key、真实受访者数据、原始访谈、第三方书籍全文/OCR/切片和内部日志不得进入公开仓库。
4. 新知识先进入私有审计区。独立审计子代理不能批准自己生成的材料；人工批准后才允许进入 Wenjin 运行时。
5. API 采用服务端 BYOK。密钥不进入前端、浏览器持久化、URL、响应、日志、审计事件或测试输出。
6. 协作 V1 只做项目/成员/角色/版本/审核/审计，不做实时共同编辑。
7. 公开推送是最后一个闸门：必须完成回归、环境、安全、版权/隐私、文档、依赖和发布审阅，并由项目创建者审阅发布报告后执行。

## 2. 当前基线和需要保留的证据

开始每个阶段前记录以下只读证据，避免把“能构建”误认为“与原 master 功能一致”：

- 后端：Python 3.12、FastAPI/SQLAlchemy/SQLite 等依赖版本、当前测试数量及结果。
- 前端：Node 22、React/Vite/TypeScript/Vitest/Playwright 版本、类型检查、测试和构建结果。
- 运行路径：SQLite/no provider、PostgreSQL+Redis/fake provider、Docker Compose smoke。
- 功能矩阵：认证、知识、问卷/访谈、田野工作、记忆、社区、Copilot、流式响应、上传和管理页面。
- 安全基线：公开树与历史 secret scan、`.env`/上传/数据库/日志排除、CORS、JWT、错误响应、对象归属。
- 原 master 对照：以私有备份和可复现实验为依据建立“保留/变化/暂不支持”矩阵；不得把不可公开的原始材料复制到新仓库。

## 3. 协作方式和代理分工

主代理负责规格落地、代码集成、最终安全审查和发布闸门。只在任务边界清晰且写集不相交时并行委派：

### 3.1 技术/环境评审子代理

权限：只读仓库审查，不改公开代码，不推送。

输出：

- 环境矩阵和启动失败点；
- 依赖、迁移、容器、CORS、上传、认证、日志和错误契约风险；
- 与当前计划的冲突、漏测和 P0/P1/P2 排序；
- 每个结论的文件/行号和复现命令。

主代理只采纳可复现、有证据的意见；不把子代理意见自动当作修复完成。

### 3.2 知识整理与审计子代理

权限：只写私有审计暂存目录，不写公开仓库运行时目录，不批准、不发布。

输出：

- 中英文候选来源登记表；
- 场域/方法/语言/许可/隐私/版本/URL 或 DOI 元数据；
- 短摘要、结构化卡片和训练/提示模板草案，不复制受版权保护的全文；
- 事实、翻译、适用边界、偏差、潜在伤害和 prompt/skill 影响审计；
- `approved | needs_review | rejected` 建议及证据链接。

知识线采用“候选收集 → 权利/隐私初筛 → 内容事实核查 → 双语检查 → 提示/skill 影响评估 → 独立审计 → 人工批准 → 版本化导入”。在主代理复核、项目创建者批准前，不得导入 Wenjin runtime。

### 3.3 代理交付规则

- 代理任务必须注明输入、输出文件、禁止触碰的路径、验证命令和停止条件。
- 代码代理若被启用，使用独立 `codex/` 分支或 worktree，写集最多覆盖一个垂直切片；主代理审查 diff、测试和安全边界后才合并。
- 任何代理不能执行公开推送、变更旧仓库可见性、删除原始备份或替用户批准材料。

## 4. 阶段和任务

### 阶段 0：冻结基线和上下文（G0）

目的：让后续代理和新会话可复现同一基线。

任务：

- `P0.1` 更新 `AGENTS.md`，登记技术栈、命令、目录边界、秘密/PII/版权红线、稳定功能保留规则和代理工作流。
- `P0.2` 生成基线报告（只读）：测试数、构建产物、路由/模型/迁移索引、原 master 功能矩阵和已知差异。
- `P0.3` 写 ADR 目录规范和第一批决策草案：服务端 BYOK、协作 V1 非实时、知识审计门、扩展不执行。
- `P0.4` 将基线命令和未解决风险写入 `tasks/todo.md`；不修改业务行为。

验收：新会话只读 `AGENTS.md`、规格、计划、todo 和 `git status` 即可接续；基线报告包含命令和原始结果；工作树无未解释文件。

### 阶段 1：平台硬化（G1）

目的：先修复会污染后续功能的环境、安全和归属基础，保持旧 API/页面可用。

#### P1. 配置、日志和错误边界

范围：配置校验、环境样例、启动诊断、request ID、统一错误 envelope、secret redaction；失败时不泄露 stack trace、环境值或 provider 响应。

候选写集：`backend/app/config.py`、`backend/app/core/*`、相关测试、`.env.example`（如存在/需要新增）。单个切片不超过 5 个文件。

验收：随机 JWT secret、无 provider key 的干净环境可启动；缺失生产必需配置快速失败；敏感值在响应/日志/异常中不可见；旧测试不回退。

#### P2. 认证、对象归属和安全输入

范围：复核 token 存储策略、CORS、JWT、上传大小/MIME/路径、URL/SSRF 边界、受保护对象的 project/user ownership；优先修复 P0/P1。兼容既有登录流程，迁移必须可回滚。

候选写集：认证/安全依赖的单一模块、对应测试、前端 client/stream 的最小改动；不同时做业务重构。

验收：双用户拒绝矩阵通过；越权读取/编辑/分享/删除均有测试；上传和外联边界测试通过；密钥不进 localStorage、URL、响应或日志；旧登录/流式路径保持可用或有迁移说明。

#### P3. 数据库、迁移和容器环境

范围：迁移可重复执行、SQLite 与 PostgreSQL 差异、Redis 可选性、Compose 健康检查、非 root/最小暴露、上传和数据库目录边界。

候选写集：迁移文件、Compose/CI 环境、环境测试；不把生产密钥写入 Compose。

验收：三种环境矩阵可记录成功/预期降级；数据库迁移从空库和已有库均可执行；服务健康检查、超时、停止和重启行为明确。

#### P4. CI 质量门

范围：在现有 CI 基础上补齐 lint、类型、测试、构建、依赖/secret/license 检查；不以放宽鉴权或删除测试来通过 CI。

候选写集：`.github/workflows/*`、依赖审计配置、必要的脚本和文档。

验收：PR/push 自动执行后端、前端、安全和文档相关门；失败可定位；不使用真实 provider key；CI 运行时间和缓存策略有记录。

### 阶段 2：知识流水线（G2）

目的：把原有训练材料、知识卡片和新研究资料变成可追溯、可撤销、默认不公开的资产。

#### K1. 知识包契约和私有暂存

新增 schema/validator/manifest 只接受结构化元数据、短摘要、短引用、方法说明和许可证据；原书籍、原始切片、日志和真实受访者数据留在私有备份或由权利人另行授权。

验收：缺来源、语言、场域、许可、脱敏或审计状态的条目不能通过 validator；默认 `needs_review`；撤销可传播到运行时索引。

#### K2. 原有材料重整

从私有备份中做清单化和分类，不把原始不可再分发内容复制到公开树。每条材料记录来源、权利、适用场域、隐私等级、处理动作和版本哈希；无法确认的只留私有审计记录。

验收：原有材料的“保留/摘要化/私有保管/拒绝公开”决策可追溯；公开知识包不含原始日志、个人信息和未知许可文本。

#### K3. 新一批中英文资料研究

使用 `deep-research`/`literature-search` 规定的检索和引用流程，优先官方开放文档、开放获取论文、公开许可方法资源和社会调查伦理/隐私规范；覆盖问卷设计、访谈、抽样、混合方法、质性编码、跨文化/跨语言、田野安全、AI 辅助研究边界等场域。

输出只进入私有审计暂存目录，至少包含中英文来源、场域标签、方法标签、许可和再分发结论、适用限制、潜在偏差、短摘要、可审计引用和训练样例草案。不得抓取或公开第三方全文。

#### K4. 独立审计和人工准入

知识审计子代理与收集代理分离；审计报告逐条核验来源、许可、事实、翻译、隐私、偏差、提示注入和 prompt/skill 越权风险。项目创建者人工批准的条目才写入版本化 `approved` manifest。

验收：运行时只加载 `approved` 且未撤销条目；报告可指出每条材料为什么准入/拒绝；审计记录和公开包不泄露私有材料。

### 阶段 3：WISE 与记忆闭环（G3）

目的：把微创新和记忆从隐式写入改为证据绑定、可解释、可撤销的提案流。

任务：

- W1：定义 proposal/experiment/candidate_memory 状态、证据、适用范围、置信度、反例、副作用、撤销和审批字段。
- W2：实现提案创建、查看、批准、拒绝、撤销和审计事件；未经批准不写长期记忆、公开知识或 skill。
- W3：用 fake provider 和 deterministic fixtures 覆盖提示注入、越权写入、过期、撤销、重复提交和失败重试。

验收：AI 输出只能进入提案；用户能看到证据和限制；批准/撤销可追溯；旧记忆读取和核心 Copilot 逻辑回归通过。

### 阶段 4：协作研究模式 V1（G4）

目的：提供最小可用的多人项目研究流程，不引入实时编辑复杂度。

任务顺序：

- C1：项目/成员/角色/邀请/归属数据模型与迁移；先写双用户拒绝测试。
- C2：研究产物版本、批注、审核任务、活动审计和撤销/删除策略；每个敏感对象强制 `project_id`。
- C3：后端 REST 路由、分页、幂等邀请、统一错误和权限矩阵；不修改旧核心路由的语义。
- C4：前端最小工作流：项目列表、成员角色、版本提交、审核、脱敏分享；默认 feature flag 关闭或仅开发环境启用。
- C5：浏览器/接口烟测，不实现实时共同编辑、不分享原始访谈和真实个人数据。

验收：两个账户无法越权访问、修改、分享或删除；版本可恢复/撤销；分享默认是脱敏派生物、可过期、可撤销并记录访问；旧单人流程不回退。

### 阶段 5：开放 API 生态 V1（G5）

目的：在服务端 BYOK 和明确边界内，让第三方客户端通过稳定契约使用受限研究能力。

任务顺序：

- A1：provider adapter contract、capability manifest、fake provider、错误 envelope、request ID、超时和有限重试；先完成契约测试。
- A2：OpenAI-compatible 与 DashScope adapter；key 只从服务端环境/受控 secret 读取；不在测试中使用真实凭据。
- A3：API gateway 的 scope、项目归属、配额、限流、审计 metadata 和 secret redaction；状态变更接口增加幂等约束。
- A4：OpenAPI 文档、schema snapshot、最小 SDK/示例和兼容性说明；只暴露声明式 provider/skill manifest。
- A5：扩展安全边界文档和拒绝测试；在独立 worker/WASM/容器隔离、签名、依赖和网络白名单完成前，禁止进程内执行第三方代码。

验收：fake provider 覆盖成功、超时、断流、配额、限流、供应商错误和重试；无 key 时安全降级；OpenAPI 与实现一致；不同 scope/项目不能越权；前端不持有 provider key。

### 阶段 6：文档、知识和技能校准（G6）

目的：逐份核准 README 与 `.md`，让专业知识和调查赋能两条主线有清晰边界。

任务：

- D1：建立 Markdown inventory，标记 owner、状态、来源、适用场域、输入/输出、隐私边界、失败条件和安全约束。
- D2：校准 README、API 文档、prompt、skill 和示例；清除过度承诺、内部机构/个人线索、真实 URL/key/路径和未授权知识。
- D3：补 ADR、变更日志、贡献指南、知识准入指南、调查伦理/隐私声明和 provider 配置说明。
- D4：文档命令、链接、OpenAPI 示例、中文/英文术语和代码片段逐项可执行验证。

验收：所有公开 README/MD 有来源和边界；没有把 prompt/skill 当成权限；文档不承诺未经验证的调查结论；Markdown/链接/示例检查通过。

### 阶段 7：最终发布闸门（G7）

目的：证明新版本稳定、轻量、可复现且适合公开。

门禁清单：

1. 后端原有回归和新增测试全绿；前端类型、单测、构建和关键浏览器烟测全绿。
2. SQLite/no provider、PostgreSQL+Redis/fake provider、Docker Compose smoke 均有成功记录或明确的非阻塞限制。
3. secret scan 覆盖当前树和历史；dependency audit、license inventory、版权/隐私清单无阻塞项。
4. 关键安全矩阵通过：认证、CORS、CSRF/ cookie 或 token 迁移、对象归属、上传、SSRF、错误泄露、限流、日志脱敏。
5. 知识审计记录、人工准入记录、运行时 manifest 和撤销测试完整；私有材料未混入公开树。
6. README、NOTICE、LICENSE、SECURITY、THIRD_PARTY_NOTICES、CHANGELOG、ADR 和回滚说明同步。
7. 先在发布分支/候选 tag 做干净 clone 验证，生成发布报告；项目创建者审阅报告并明确批准后，普通推送到 `origin/main` 和 tag。

## 5. 每个切片的执行协议

对每个任务执行：

1. 读取任务涉及的实际源文件、相关测试和一份同类实现；不凭记忆发明框架 API。
2. 先写失败测试或契约，再写最小实现；新能力默认安全关闭。
3. 运行受影响的最小验证，再运行阶段基线；检查 `git diff --check` 和 staged secret scan。
4. 做一次正确性、可读性、架构、安全、性能和回滚审查；发现 Critical/Required 必须修复。
5. 使用 `feat/fix/refactor/test/docs/chore` 原子提交；提交前列出改动、刻意未改动部分和潜在风险。
6. 每两到三个切片形成检查点，更新 `tasks/todo.md`、变更日志或 ADR；不要积累无法定位的大 diff。

## 6. 依赖、停止条件和回滚

依赖：平台硬化完成后才把新知识导入运行时；知识和平台门禁通过后才落 WISE；协作权限模型通过后才开放 API；所有模块通过后才进入发布闸门。

停止条件：出现未解决的 P0 安全问题、未知真实密钥、未确认版权/个人信息、越权测试失败、基线回归失败、迁移不可逆或代理输出无法复现时暂停相关阶段，保留当前提交并报告证据。

回滚：每个切片以原子提交为保存点；数据库迁移提供向前/向后策略；新能力由 feature flag 或配置关闭；发布失败时优先禁用 flag/回退候选 tag，禁止强推覆盖历史。

## 7. 计划验收

本计划获批后，才开始创建技术评审和知识审计子代理、编写模块规格和实现代码。计划批准不等同于公开发布批准；公开推送必须等待 G7 发布报告和项目创建者单独确认。
